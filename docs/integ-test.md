# Integration Test Design: LTEmbed

## 1. Objectives and Scope

The goal of this integration testing phase is to verify that the library components — tokenization, the LTEmbed BERT backend, pooling, and normalization — work together correctly through the `ZeroVecEngine` public API.

**In-Scope:**

- **End-to-End Mathematical Parity:** `ZeroVecEngine::embed()` must produce embeddings with cosine similarity > 0.999 compared to the reference Python `transformers` implementation.
- **Cold Start Simulation:** `ZeroVecEngine::new()` must successfully memory-map the `.safetensors` file and return a ready engine.
- **Error Handling:** The library must return typed `LTEmbedError` variants — no panics, no generic failures — when given invalid inputs or missing files.

**Out of Scope:**

- Unit testing of individual trait implementations — covered by `cargo test --lib`.
- End-to-end testing of example and benchmark entry points beyond compile and smoke verification.
- Deployment infrastructure outside this repository — covered separately where applicable.
- Sustained load — covered by separate benchmarks (`cargo bench`).

---

## 2. Test Environment

- **Framework:** Rust `cargo test` in `tests/` (crate treated as external library via the `[lib]` target).
- **Architecture:** Apple Silicon (aarch64) is a good local proxy for ARM64 deployment targets.
- **Golden Dataset:** `tests/fixtures/test_fixtures.json` — (input text, expected embedding) pairs generated by running e5-small-v2 through the official Python `transformers` library. Committed to the repo; treated as the source of truth for numeric correctness.

### Test Tiers

| Tier | Requires `model.safetensors` | Runs in CI | Coverage |
|---|---|---|---|
| **Tier 1 — Always** | No | Yes | Error handling, missing-file behavior |
| **Tier 2 — With assets** | Yes | No (developer / staging) | Golden parity, correct embeddings, edge cases |

---

## 3. Core Test Scenarios

### Scenario A: Golden Path Parity

**Tier:** 2 (requires model assets)

Verifies the complete library pipeline: Tokenization → BERT Forward Pass → Pooling → L2 Normalization.

**Pre-condition:** `assets/model.safetensors`, `assets/tokenizer.json`, `assets/config.json`, and `tests/fixtures/test_fixtures.json` all exist.

**Action:** Initialize `ZeroVecEngine`, call `embed()` for each input in `test_fixtures.json`, compare to the Python reference.

**Assertion:**

$$cosine\_similarity(v_{rust},\ v_{python}) > 0.999$$

for every fixture entry.

---

### Scenario B: Output Properties

**Tier:** 2 (requires model assets)

Verifies properties of the returned `Vec<f32>` that must always hold, independent of input content.

| Property | Assertion |
|---|---|
| Dimension | `v.len() == 384` |
| L2-normalized | `v.iter().map(\|x\| x*x).sum::<f32>().sqrt() ≈ 1.0 ± 1e-5` |
| `embed_batch` consistency | `embed_batch(&["a","b"])[0] == embed("a")` |

---

### Scenario C: Error Handling

All Tier 1 — always run, no model assets required (except C2 which needs the tokenizer).

#### C1: Missing Model Files

**Action:** Call `ZeroVecEngine::new()` with a non-existent `safetensors_path`.

**Assertion:** Returns `Err(LTEmbedError::ModelLoad(_))`. No panic.

---

#### C2: Input Exceeds Token Limit

LTEmbed is a library — it does not silently modify caller input. Overlong text must produce an explicit, typed error.

**Action:** Call `HFTokenizer::encode()` (or `ZeroVecEngine::embed()`) with ~10,000-word text against a 512-token limit.

**Assertion:** Returns `Err(LTEmbedError::InputTooLong { tokens, max })`.
- `tokens > 512`
- `max == 512`
- No panic, no truncated-but-`Ok` result.

---

#### C3: Malformed `config.json`

**Action:** Call `ZeroVecEngine::new()` with an invalid JSON string as `config_json`.

**Assertion:** Returns `Err(LTEmbedError::ModelLoad(_))`. No panic.

---

## 4. CI / Full Test Suite

### CI (Tier 1 only — no model weights required)

```bash
cargo test --lib
cargo test --test integration_tests test_missing_model_file_returns_model_load_error
cargo test --test integration_tests test_long_input_returns_input_too_long_error
```

### Full Suite (Tier 1 + 2 — developer / staging)

Ensure model assets are present and `test_fixtures.json` is up to date:

```bash
python3 scripts/generate_fixtures.py   # if fixtures need regenerating
cargo test --test integration_tests
```

All Tier 2 tests must pass before merging changes to the inference pipeline.

## 5. Practical Notes

- `config.json` and `tokenizer.json` are committed in `assets/`.
- `model.safetensors` is required for parity and output-property tests.
- The root [`README.md`](../README.md) documents the intended Rust API usage shape that these tests protect.
