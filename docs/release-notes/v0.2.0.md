# LTEmbed v0.2.0

LTEmbed 0.2.0 replaces the model. It embeds with EmbeddingGemma 2
([`google/embeddinggemma-2`](https://huggingface.co/google/embeddinggemma-2)), from
Unsloth's `UD-Q5_K_XL` GGUF, and no longer loads the previous model, Jina v5 Nano
(`jinaai/jina-embeddings-v5-text-nano-retrieval`), or a 0.1.0 bundle. There is no
dual-model mode.

**Vectors from 0.1.0 cannot be reused: rebuild every index before you switch.** The
[migration guide](https://github.com/Lychee-Technology/LTEmbed/blob/v0.2.0/docs/model-migration.md)
has the steps.

## Before you upgrade

- **Rebuild your indexes.** Jina and EmbeddingGemma 2 vectors are in unrelated spaces, but
  both are 512 wide by default and unit length. An index that checks only the dimension
  accepts a mix of them without an error and then returns wrong neighbours. Re-embed every
  document and every cached query into a new index, and switch queries and documents to it
  together
  ([Moving an index](https://github.com/Lychee-Technology/LTEmbed/blob/v0.2.0/docs/model-migration.md#moving-an-index)).
- **Keep one quant per index.** Vectors of different GGUF quants of EmbeddingGemma 2 do not
  belong in one index either: at 512 dimensions, the `UD-Q4_K_XL` and `UD-Q5_K_XL` vectors
  of the same short text are as far apart as cosine 0.946. Tag each index with the new
  `EmbeddingEngine::embedding_space()`, which names the sha256 of `model.gguf`, the prompts,
  `output_dimension` and `l2_normalize`, and compare the tag before every write and search.
- **Use a new bundle.** A 0.1.0 bundle fails to load (`UnsupportedPooling`). Use the bundle
  in the release tarball, or assemble one from the pinned revisions with
  `python3 scripts/assemble_gguf_bundle.py gguf_bundle`
  ([bundle format](https://github.com/Lychee-Technology/LTEmbed/blob/v0.2.0/docs/bundle-format.md#assembling-a-bundle)).
- **Re-tune score thresholds and recount tokens.** Similarity values differ between the
  models, so a cut-off tuned on Jina scores has to be tuned again. The limit is still 8192
  tokens, but the tokenizer is different, so the same text can have a different count;
  `EmbeddingEngine::token_count` is the engine's own count.

## Prompts are applied for you

Wrap search text in `EmbeddingInput::query` and the passages you search over in
`EmbeddingInput::document`. The engine adds EmbeddingGemma 2's prompts itself:
`task: search result | query: ` and `title: none | text: ` (`QUERY_PREFIX` and
`DOCUMENT_PREFIX`, which were `Query: ` and `Document: `). Pass the text alone: a text that
already starts with a prompt gets it twice. Any other component that embeds text with its
own prompts, such as a Python job using the model directly, must use these.

## Memory

Peak memory grows with the longest input an engine has embedded, and the engine keeps that
peak until it is dropped. An 8192-token input needs about 1.6 GB. Inputs longer than the
bundle's `max_length` fail with `InputTooLong` and are never truncated, so a lower
`max_length` in `build-info.json` caps the peak:

| `max_length` | Peak resident memory, x86-64-v3 |
|---|---|
| 512 | 0.34 GiB |
| 1024 | 0.40 GiB |
| 2048 | 0.51 GiB |
| 4096 | 0.77 GiB |
| 8192 (release bundle) | 1.38 GiB (1.48 GB) |

On aarch64 the peak was 0.09 GiB higher at every input length measured: 1.47 GiB (1.58 GB)
for 8192 tokens.

**On a memory-limited host such as AWS Lambda, set `max_length` to 2048** if your inputs
fit in it. That caps the peak at about 0.5 GiB on x86-64-v3, and about 0.6 GiB on aarch64,
an estimate that adds the 0.09 GiB. These are Linux process measurements, not Lambda ones,
and they leave out your application's own memory. Editing `build-info.json` breaks its line
in `SHA256SUMS`, so check the bundle before you edit it.

The table was measured with static llama.cpp `v0.1.159-3`. `v0.1.160-1`, which 0.2.0 builds
against, peaks within 0.001 GiB of it on x86-64-v3
([details](https://github.com/Lychee-Technology/LTEmbed/blob/v0.2.0/docs/architecture.md#long-inputs-and-memory)).

## API changes

Code that embeds only through `EmbeddingEngine`, `EmbeddingInput::query`,
`EmbeddingInput::document` and `EngineConfig` compiles unchanged. Code that names a removed
or changed item does not:

- **`HFTokenizer` is removed**, with the whole `ltembed::traits` module (`Tokenizer`,
  `TokenizerOutput`). The engine tokenizes with the GGUF's own vocabulary, and the library
  no longer depends on `tokenizers`. Count tokens with `EmbeddingEngine::token_count`
  ([Counting tokens](https://github.com/Lychee-Technology/LTEmbed/blob/v0.2.0/docs/model-migration.md#counting-tokens)).
- `ltembed::benchmarking::scenario_token_lengths` and `BENCHMARK_MAX_LENGTH` are removed.
- `InferenceError::SequenceTooLong` and `InferenceError::AllPadding` are removed: an input
  over `max_length` is `LTEmbedError::InputTooLong`, as before. `InferenceError::Tensor` is
  folded into `InferenceError::Backend`.
- `LTEmbedError::InputTooLong` is `{ tokens: Option<usize>, bytes: usize, max: usize }`
  instead of `{ tokens: usize, max: usize }`. `tokens` is `None` for an input too large to
  fit in `max` tokens at all, more than `max` × 93 bytes with its prefix, which the engine
  rejects without tokenizing it.
- `EmbedBatchProfile::tensorize_ms` and `extract_ms` are removed; they were always 0 with
  llama.cpp.
- `QUERY_PREFIX` and `DOCUMENT_PREFIX` hold the new prompts.

Added:

- `EmbeddingEngine::embedding_space()` and `EmbeddingSpace`: what an engine's vectors
  depend on, with a string form to store with an index
  ([Embedding space](https://github.com/Lychee-Technology/LTEmbed/blob/v0.2.0/docs/architecture.md#embedding-space)).
- `EmbeddingEngine::token_count(input)`, an input's token count as `embed` counts it,
  prefix, `<bos>` and `<eos>` included, and `EmbeddingEngine::max_length()`, the bundle's
  limit.

Tokenizing no longer takes the engine's lock. An engine still encodes one input at a time,
under a mutex, and `token_count` never waits for it.

## Bundle and build

- A bundle is `model.gguf` and `build-info.json`, with `SHA256SUMS` and `provenance.json`.
  It has no `tokenizer.json`. `build-info.json` no longer has `output_embedding_dimension`;
  a bundle that still has it loads, and the field is ignored.
- 0.2.0 links static llama.cpp `v0.1.160-1` (llama.cpp `v0.7.0`) from
  [`Lychee-Technology/static-llama-cpp-rs-builder`](https://github.com/Lychee-Technology/static-llama-cpp-rs-builder/releases/tag/v0.1.160-1):
  point `STATIC_LLAMA_DIR` at its `aarch64-graviton2` or `x86_64-v3` variant
  ([setup](https://github.com/Lychee-Technology/LTEmbed/blob/v0.2.0/docs/development.md#static-llamacpp-artifacts)).
  It builds on aarch64 Linux and x86-64-v3 Linux, as 0.1.0 did.

## Release tarball

`ltembed-0.2.0-unsloth__embeddinggemma-2-GGUF-UD-Q5_K_XL.tar.gz`, with its `.sha256`. The
name no longer ends in `-linux-arm64`: the tarball holds the source code and the bundle,
which build and load on both platforms, and no compiled binary or static llama.cpp
archives.

```bash
sha256sum -c ltembed-0.2.0-unsloth__embeddinggemma-2-GGUF-UD-Q5_K_XL.tar.gz.sha256
tar -xzf ltembed-0.2.0-unsloth__embeddinggemma-2-GGUF-UD-Q5_K_XL.tar.gz
cd ltembed-0.2.0-unsloth__embeddinggemma-2-GGUF-UD-Q5_K_XL/gguf_bundle && sha256sum -c SHA256SUMS
```
